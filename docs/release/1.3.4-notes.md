# VRMC 1.3.4 release notes (bug-fix build on 1.3.3)

Status: bug-fix release candidate for the Apple Vision Pro D1 sideload build (development signing,
team <TEAM_ID>). 1.3.4 fixes the defects found in the live 1.3.3 headset run and the reviewer
findings left open by 1.3.3.

## What was broken and is now fixed

### 1. Duplicate window scenes (HIGH - 1.3.3 device regression)
The 1.3.3 run restored **eight** .windowApplication scenes (16 UIWindows): every window session left
behind by earlier launches came back with its own SwiftUI RootView, its own hidden launcher host and
its own setup-refresh loop. Now:
- a runtime window-scene guard keeps exactly one .windowApplication scene and destroys the extra
  scene sessions (the immersive space is a separate scene role and is never touched - the shipped
  plist keeps UIApplicationSupportsMultipleScenes=true because the immersive space needs it);
- only the primary RootView mounts the hidden launcher host / setup loop (duplicates stay inert and
  are pruned); state log lines are capped instead of repeating every scene;
- the launch storm's two full-app inactive flaps are expected to disappear with it.

### 2. Play -> VR auto-open made the user press "Enter VR" (HIGH UX)
In 1.3.3 the automatic open waited ~14 s for the first game picture while the Play tab offered an
"Enter VR" button - the natural thing to press, and it pre-empted the automatic attempt. Now the
Play tab shows the automatic stage ("Waiting for the game picture..." -> "Entering VR...") with a
spinner instead of the button, and only offers "Enter VR now" after a 25 s bounded fallback; a manual
press still cancels the automatic attempt cleanly. The wait task is cancelled when the game starts
through another path (no stale 180 s poll).

### 3. Misleading teardown logs (LOW)
The game-stop path reset the presenting flag before the compositor's end notification, so a session
that presented 19,517 frames logged "presentation never confirmed" and a duplicate "immersive space
dismissed" line. The true presented state and a single dismissal line are now logged.

### 4. Reviewer findings from REVIEW_1.3 §5 (all fixed, host-tested)
- **R1** right-pinch carry only armed when the pinch was still held on the GUI-transition frame; a
  pinch released on the exact open/close frame could become a world place/attack. New
  PinchCarryGuard also arms from the previous frame; 34 checks.
- **R2** quick-menu vignette ladder now {0, .3, .5, .7, .9}: a launcher-written 0.90 reads as
  "Strong" and stores 0.90 (was displayed as Strong but stored 0.70); 29 checks.
- **R3** quick-menu button is placed against the pause screen's real widget rectangles, so it no
  longer overlaps the bottom vanilla/Vivecraft row on small GUI scales; 17 checks.
- **R5** a transient reflective injection failure no longer disables the in-VR quick-menu button for
  the session (cooldown retry on the same screen, immediate retry on a new screen); 15 checks.
- **R6/R12** the M4 fallback snap turn now shares the seated-path deferral: a left-middle double tap
  is exactly one right turn (previously left+right = net zero); 21 seated-turn checks.
- **R7** Vivecraft download now writes buffered data chunks instead of iterating AsyncBytes one byte
  at a time (tested against a local HTTP server: full file, 404 rejected, oversized rejected).
- **R8** Vivecraft install moves old jars aside and restores them on failure instead of deleting
  them before the new jar is in place.
- **R9** the Vivecraft hash cache is main-actor-only (no background write race).
- **R10** import validates the picked file as a real zip with a fabric.mod.json, and only the pinned
  download is called SHA-verified (import of the pinned copy is "the tested build", other jars are
  "not the tested build").
- **NEW-4** vrmc-status.json reports "runningOnVisionOS":"visionOS" instead of "Mac OS X".

### 5. Purple flash on immersive menu/pause (investigated, instrumented; not fixed visually)
The M8 report is **not** explained by the release compositor path: the sessions where it was reported
had no developer surfaces active, and the 1.3.3 release run shows no test pattern/probe/clear and every
eye-texture swap held the last good frame. The only correlated change is the hardware sRGB texture
view (M8 session), whose stale-view hazard the 1.3 checkpoint already hardened. 1.3.4 adds
release-neutral instrumentation (per-eye swap logging keyed on texture handles, sRGB view-cache
format/extent validation and per-rebuild logging, and a diagnostics-only drawn-frame probe on the
3 frames after each swap) so the next device run can prove or exonerate the compositor; triage rule and
capture protocol are in docs/plan/RENDER_BUGFIX.md. No visual behaviour was guessed.

## Known limitations carried

- Immersive rendering is capped at 90 Hz by visionOS for this presentation path (M8 A8).
- Bow visual model orientation is a Vivecraft-side rendering behaviour (first-person BOW_* transforms
  are hard-coded in hand-local space); the provider only supplies the hand pose, so it cannot change
  the bow-vs-hand angle. Deferred with the analysis in the provider report.
- The development provisioning profile expires **2026-11-15T03:21:06Z**; Xcode re-issued the same
  profile (no extension possible before expiry) - re-sign after that date or the app will stop
  launching.
- `devicectl device process launch` remains broken for all apps on this host/D1 pairing; launch from
  the headset Home View.
- M7 gesture-accuracy residuals from M7_ACCURACY_ITERATION.md are unchanged (no tuning without
  device data).
- The purple flash remains unconfirmed on the release path until a device run with the new
  instrumentation (see docs/plan/RENDER_BUGFIX.md triage protocol).
